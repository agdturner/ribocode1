    Setup

    Follow the Developer Quick Start Guide

    Mol* Submodule Workflow

    For routine Ribocode development, use the pinned Mol* commit at packages/molstar. Do not switch to a moving master or ribocode branch just to run or test Ribocode. A detached HEAD in the submodule is normal. After switching or updating the Ribocode branch, save any local Mol* work before restoring the recorded checkout from the Ribocode root:

    git submodule update --init --recursive
    git submodule status -- packages/molstar

    If you previously made commits in a detached HEAD, put them on a branch before updating. Rebuild the Mol* library if the checked-out commit changes.

    To contribute changes to Mol*, fork the shared Ribocode Mol* repository. In the submodule, configure origin as your personal Mol* fork and upstream as the shared Ribocode Mol* repository. For a newly initialized checkout, run these from the Ribocode root (if upstream already exists, verify its URL instead of adding it again):

    git -C packages/molstar remote set-url origin https://github.com/<your-github-user>/molstar.git
    git -C packages/molstar remote add upstream https://github.com/ribocode-slola/molstar.git
    git -C packages/molstar remote -v

    For changes to the version currently pinned by Ribocode, start from the shared 5.13.1-based branch; the shared fork's master is currently based on 5.4.2. There is no need to update or push your personal master:

    git -C packages/molstar fetch upstream
    git -C packages/molstar switch --no-track -c my-molstar-change upstream/investigate/ribocode-on-5.13.1

    Commit your Mol* changes on the feature branch, push it with git -C packages/molstar push -u origin my-molstar-change, and agree the appropriate shared-fork target before opening a PR. Do not assume that master contains the version currently pinned by Ribocode.

    To update Ribocode's pin after the Mol* PR merges, start a Ribocode feature branch. Fetch the shared Mol* fork, check out the intended merged Mol* commit in the submodule, rebuild its library, and run npm run test:pr from the Ribocode root. Stage packages/molstar to record the new pin, then submit it in a Ribocode PR. Do not pin a commit that exists only on a personal fork.

    Keep the tracked .gitmodules URL pointed at https://github.com/ribocode-slola/molstar. Personal fork URLs belong in local Git configuration only.

    Build and run locally

    Local Development

    From the Ribocode root directory:

    • npm install
      • Installs all dependencies.
    • npm --workspace packages/molstar install
      • Installs Mol* workspace dependencies (useful for first-time setup and after Mol* dependency updates).
    • npm --workspace packages/molstar run build:lib
      • Builds the packages/molstar/lib output that Ribocode imports from.
      • Run this at least once after cloning Mol* and again after any Mol* source changes.
      • Equivalent from within packages/molstar: npm run build:lib.
    • npm run dev
      • Starts the Vite development server using settings from .env (base path is /).
      • Visit the local URL shown in the terminal (usually http://localhost:5173/).

    Production Build and Preview

    • npm run build
      • Builds the app for production using settings from .env.production (base path is /ribocode1/).
      • Regenerates TypeDoc output first (npm run docs) to ensure deployed docs stay in sync with source.
      • Output is placed in the dist/ directory.
    • npm run preview
      • Serves the production build locally for testing (simulates deployment).
      • Visit the local preview URL (usually http://localhost:5173/ribocode1/).

    Notes on Environment Files

    • .env is used for local development (base path /).
    • .env.production is used for production builds (base path /ribocode1/).
    • The correct environment file is automatically picked up by the npm scripts.
    • Runtime browser code must use Vite environment access (import.meta.env.*) rather than CRA-style process.env.*.
    • Service worker registration paths should be derived from import.meta.env.BASE_URL to avoid incorrect URLs on GitHub Pages subpaths.

    Deployment overview

    The deployment command builds the app and includes the generated API docs. See Deployment to choose between your fork's test site and the official site.

    Source Code Overview

    Configuration files are in the top-level directory. The main source code is in the src directory, with additional dependencies in packages.

    • Ribocode Mol* is located in the packages/molstar directory.
    • The src directory contains:
      • App.tsx: The top-level application component, responsible for composing the main UI and wiring together state, providers, and layout.
      • App.css: Global CSS for styling all components.
      • App.test.tsx: Basic test for the App component.
      • session.integration.test.tsx: Integration tests for session-related flows, such as session load/save, file input triggers, and modal appearance. Use this file for tests that simulate user workflows involving session management, rather than placing them in App.test.tsx or App.integration.test.tsx.
      • components/: UI components, including ViewerColumn, GeneralControls, AppHeader, and others. Each major component typically has a corresponding .test.tsx file for tests.
      • context/: React context providers and objects for sharing state and logic (e.g., SelectionContext, SyncContext, ViewerStateContext).
      • handlers/: Event and UI handler logic, such as uiHandlers.ts for shared UI event logic.
      • hooks/: Custom React hooks for encapsulating stateful logic and side effects (e.g., useMolstarViewer, useMoleculeLoader, useUpdateColors, useSessionSave, etc.).
      • constants/: Centralized runtime constants (e.g., ribocode.ts for alignment and viewer key constants).
      • types/: Shared TypeScript types and interfaces (e.g., ribocode.ts for core app types, molstar.d.ts for Mol* types).
      • utils/: Utility functions and helpers for data processing, color themes, structure manipulation, and viewer helpers. Includes files like chain.ts, residue.ts, colors.ts, data.ts, dictionary.ts, and viewerHelpers.ts (with corresponding test files).
      • main.tsx: Entry point for the React application. Renders the root App component and applies global styles.
      • service-worker.ts: The PWA service worker for offline support and caching.
      • serviceWorkerRegistration.ts: Registers or unregisters the service worker as needed.

    The repository-root public/ directory contains static assets for the PWA.

    Notes:

    • Some UI components for loading dictionary/alignment data and for advanced visualization controls (e.g., fog, camera planes) exist but may be hidden or under development.
    • All major logic is modularized for maintainability, with helpers, types, and constants extracted to their own files.

    Theme System Architecture (Important)

    This section defines expected behavior for loading, applying, saving, and testing themes.

    Dataset-role ownership

    • AlignedTo is loaded in Column A (Load AlignedTo).
    • Aligned is loaded in Column B (Load Aligned).
    • Theme assets (loaded color maps) are shared globally and can be applied to either role.
    • Representation theme callbacks must preserve the caller's role intent (AlignedTo vs Aligned).

    Where behavior is implemented

    • High-level wiring and state orchestration: src/App.tsx.
    • Representation UI controls: src/components/Molecule.tsx.
    • Column composition and role wiring: src/components/ViewerColumn.tsx.

    Theme controls model

    • Global controls in Representation Controls (Theme section):
      • Select current chain/residue theme.
      • Load, Save, and remove (x) actions.
      • These values drive defaults for new representations.
    • Per-representation controls in each representation row:
      • Theme Type (chain or residue-type).
      • Chain Theme / Residue Theme selectors.
      • These are authoritative for that representation.

    Representation theme switching contract

    • Switching a representation between chain and residue-type must update the existing representation in place.
    • Do not recreate/delete-add a representation just to apply a theme change.
    • Representation identity (repId) should remain stable across Theme Type switches.
    • Residue theme apply path should use the same in-place update model as chain theme applies.

    Residue theme selection behavior

    • If a mode-selected residue theme is available, switching Theme Type to residue-type should prefer that selected residue theme.
    • If no valid selected residue theme is available, fall back to the mode-specific default residue theme.
    • Loading and selecting a new residue theme while already in residue-type mode must apply immediately without requiring a Theme Type toggle.

    Residue default mapping contract

    • UI selection value default must resolve to role-specific registered theme names:
      • AlignedTo-default-residue-colors for AlignedTo.
      • Aligned-default-residue-colors for Aligned.
    • Regressions usually appear when a callback resolves or applies the wrong role for a representation update.

    Residue visual refresh note

    • Apply the target residue theme directly, with a fresh __ribocodeThemeRefreshNonce.
    • The residue provider declares the refresh nonce and __ribocodeActiveThemeKind as hidden Mol* parameters and retains them in its theme props. Undeclared parameters are stripped by Mol* and cannot invalidate cached colours or preserve session metadata.
    • Queue residue-theme requests until both source and mirrored updates have completed. Do not expose an intermediate neutral theme in the selection controls.
    • Session serialization also recognizes registered residue-theme names when older representation metadata is absent.
    • When a session references files already open, reuse their structures but restore the saved representations rather than skipping the session state.

    Chain-colour identity note

    • Chain edits target author chain IDs. Label aliases may be updated only when they do not collide with another author chain ID.
    • When seeding an editable default theme, preserve provider colours for all unaffected chains; author-ID colours take precedence over colliding label aliases.

    Sync scope note

    • Sync currently describes camera synchronization behavior.
    • Theme application logic may still update corresponding representations across viewers, but this should not violate role ownership or mode intent.

    Testing implications for theme regressions

    • Prefer representation identity assertions (repId) over positional/index assertions.
    • In Playwright, avoid selectors that assume dataset role is encoded in representation row IDs unless that is explicitly true in code.
    • For debugging, use window.__ribocodeTestApi.getRepresentationThemeStates(mode, viewerKey?) and assert by repId and viewer.

    Mol* Advanced Controls Toggle

    To reduce UI clutter for common workflows, each viewer column includes a dedicated advanced-controls toggle for the embedded Mol* interface.

    • The button is rendered in ViewerColumn and defaults to collapsed:
      • Label when collapsed: Show Advanced Mol* Controls
      • Label when expanded: Hide Advanced Mol* Controls
    • MolstarContainer disables the embedded layout regions and their native toggle; the viewport controls remain available.
    • MolstarAdvancedControls renders the sequence, left panel, structure tools and log below the viewer only when the Ribocode toggle is expanded.
    • The pinned Mol* light skin is imported before App.css; scoped overrides adapt the viewport and advanced panels to the two-column layout.

    This keeps default user workflows focused on Ribocode controls while preserving full Mol* UI access for advanced users.

    UI Element ID and Test ID Conventions

    To ensure robust, maintainable, and testable UI code, Ribocode uses the following conventions for element IDs and data-testid attributes:

    General Rules

    • IDs should be unique, predictable, and use kebab-case (e.g., viewer-column-a-load-btn).
    • data-testid attributes should be added to all modal fields, file inputs, and dynamic elements that are targeted in E2E/component tests.
    • Use data-testid for elements that may have dynamic content, multiple instances, or where IDs are not unique.
    • Prefer data-testid in Playwright and Testing Library selectors for E2E and integration tests.

    Examples

    Modal Components

    <input type="file" id="session-modal-alignedto-input" data-testid="session-modal-alignedto-input" />
    <button id="session-modal-load-btn" data-testid="session-modal-load-btn">Load Session</button>

    Viewer Column Buttons

    <button id="viewer-column-a-load-btn" data-testid="viewer-column-a-load-btn">Load AlignedTo</button>
    <input id="viewer-column-a-file-input" data-testid="viewer-column-a-file-input" type="file" />
    <button id="viewer-column-a-advanced-molstar-controls-toggle-btn" data-testid="viewer-column-a-advanced-molstar-controls-toggle-btn">Show Advanced Mol* Controls</button>

    General Guidelines

    • Always use the same value for id and data-testid when possible for clarity.
    • Document any new IDs or data-testid attributes added to components.
    • Update tests to use these selectors instead of brittle text or class selectors.

    Updating Existing Components

    If you add a new modal, file input, or dynamic UI element, ensure it has a data-testid attribute following the conventions above. Update the relevant tests to use these selectors.

    Tooltip Conventions

    Use concise, state-aware tooltip text for interactive controls:

    • Action-first wording for enabled controls (for example, "Zoom to...", "Load...", "Save...").
    • Current-state wording for toggles and mode selectors (for example, On/Off or current selected mode).
    • Disabled guidance for blocked controls, explicitly stating what prerequisite must be met.

    Implementation guidance:

    • Prefer title attributes on controls and, where native browser behavior is inconsistent for certain elements (for example disabled/select controls), also place matching tooltip text on a wrapper or label.
    • Keep wording consistent across parallel controls (Select 1/Select 2, AlignedTo/Aligned) by reusing shared helper functions.

    Testing guidance:

    • Add focused assertions for tooltip text in the nearest component/integration test file.
    • Verify both enabled and disabled-state wording when behavior changes by state.

    Molstar

    Ribocode currently uses a customised Mol* 5.13.1, pinned as a submodule to commit 901cef218be8f231ebb749160e83d586be77ab34 in the Ribocode Mol* fork. The commit is available on its investigate/ribocode-on-5.13.1 branch. Keep that branch available while Ribocode depends on the pin. The shared fork's master is currently based on 5.4.2, not the version Ribocode is using. The submodule gitlink, rather than a moving branch name, determines the actual version.

    Compared with the official Mol* 5.13.1 tag, this pin adds the Ribocode extension under src/extensions/ribocode, the big.js dependency and a TypeScript build setting; it does not change existing Mol* core source files. The extension includes the molecule loader and trajectory provider, alignment types, geometry and its regression tests. Its geometry includes the rigid-transform centroid fix needed by Ribocode.

    An earlier attempt to contribute the extension upstream is recorded in Mol* PR #1726. Reviewers raised concerns about adding big.js to the library. Ribocode is retaining the customised setup for now; neither upstream acceptance nor a move out of the fork should be assumed.

    Important local wiring details:

    • Ribocode resolves molstar imports to packages/molstar via vite.config.js aliasing.
    • Ribocode imports from molstar/lib/..., so the local packages/molstar/lib tree must exist.
    • The Mol* repository keeps lib/ out of Git; generate it locally with npm run build:lib in packages/molstar.
    • If you edit files under packages/molstar/src, rebuild Mol* (npm run build:lib) before re-testing Ribocode.

    Possible future move to stock Mol*

    Moving the extension into Ribocode and using stock Mol* 5.13.1 appears feasible, but has not been implemented or validated. A trial should use an isolated branch and preserve the existing setup as a comparison:

    1. Move the loader, trajectory provider, alignment types, geometry, QCProt helper and their tests into Ribocode; change the application's imports and test mocks. Preserve the centroid fix and existing loading and alignment behaviour.
    2. Replace the customised submodule with an explicitly pinned stock Mol* dependency or checkout. Adjust the workspace, lockfile, TypeScript project references, Vite alias and build instructions as appropriate. The extension and other Ribocode code use molstar/lib APIs, so removing the fork would not eliminate all coupling to Mol* internals.
    3. Keep big.js as a Ribocode dependency initially if retaining current arithmetic. It is used in centroid and mean calculations and in a rotation helper. Assess whether it is needed in each path before replacing it: compare numerical accuracy, runtime and bundle size on representative inputs. Extracting library code is not automatically simpler and would require licence compliance and maintenance; alternatives such as native numbers or compensated summation must be measured, not assumed equivalent.
    4. Validate clean installation, type-checking and builds, geometry and integration tests, and forced-WebGL browser checks for loading, centring, alignment, selection and session round trips. Compare actual transformed coordinates and fit metrics with the current pin, including the cases in the alignment testing reference.

    This is a possible maintenance simplification, not a decision to promote the experimental alignment paths or to upgrade to Mol* 6.

    UniProt Lookups and Chain Labels

    Ribocode enriches chain labels with available ribosomal protein (RP) family names, UniProt accessions, gene names and mmCIF molecule descriptions. This is display metadata; it is not a prerequisite for loading or aligning structures. The User Guide describes the visible labels and controls.

    Mapping chains to accessions

    • rpNameTable.ts reads Mol* model _struct_ref and _struct_ref_seq categories to map entities and author chain IDs to accessions. uniprot.ts also parses uploaded mmCIF text for chain mappings, including loop and single-item references.
    • These mapping paths accept only accession-shaped values. An explicitly non-UniProt _struct_ref.db_name is excluded, including its linked _struct_ref_seq rows, even if an identifier looks like a UniProt accession. Missing or unknown database identity is treated as a fallback: a valid-looking identifier is accepted, but its format does not prove it is a UniProt accession or that it exists.
    • chain.ts combines the mappings with RP_name_table_uniprot.csv to find RP family names. It uses a species-specific lookup where possible, with an all-species fallback. It also incorporates available molecule descriptions and gene names. The accession toggle affects label display; it does not disable background lookups.

    Discovery, requests and caching

    App.tsx queues accessions from structured chain mappings parsed from uploaded mmCIF-like files. Chain information extracted from Mol* models can also discover accessions. Arbitrary accession-shaped text outside these mappings is not queued. References with unknown database identity remain a format-only fallback, so those queries are not guaranteed to be UniProt.

    The background queue deduplicates pending, in-flight and cached entries. The app requests gene names from the UniProt REST API in batches of 20, with a 1.2-second delay between batches, and updates labels as results arrive. Requests send accession strings to UniProt; the entire structure file is not sent by this lookup. An internet connection and a successful UniProt response are needed for newly resolved gene names.

    Results, including missing names represented by null, are kept in memory. Successful nonempty gene names are also stored in browser local storage and restored from saved sessions; null entries are not restored. A failed batch is currently recorded as null for each accession, indistinguishable in the cache from an accession with no returned gene name. Consequently it is not automatically retried while that null remains in memory. A reload or session restore can allow a later discovery to retry it.

    The UI reports cached, pending and in-flight counts; a completed entry does not necessarily mean a gene name was found. Browser console [UniProt] messages help trace discovery and batches, and the Network tab can reveal HTTP errors. For regressions, see uniprot.test.ts, rpNameTable.test.ts, and uniprot-reference-filter.e2e.spec.ts.

    Highlighting and Selection Colouring

    Ribocode currently supports two distinct visual mechanisms for selected features:

    • Halo-style marker highlighting (Mol* marker channels). This is the bright visual emphasis users typically interpret as "highlight".
    • Surface recolouring (overpaint). This changes rendered colours of selected regions and is useful for categorical/layered selection colouring.

    Current implementation intent:

    • Keep deterministic selection ordering (subunit, then chain, then residues) for predictable overlap behavior.
    • Preserve halo-style highlighting for immediate focus cues.
    • Support per-level colour overlays where useful for structural context.

    Important Mol* constraint:

    • Marker highlight/select colours and strengths are renderer-global per viewer (highlightColor, selectColor, highlightStrength, selectStrength).
    • This means multiple simultaneous marker halo colours per level are not available through default marker channels alone.

    Practical strategy:

    • Use halo markers as the primary "highlight" cue.
    • Use overpaint to encode level-specific colouring when needed.
    • Optionally dim unselected regions to a common neutral colour to increase contrast for selected features.

    Potential "dim unselected" directions:

    • Renderer-level dimming (dimColor, dimStrength) when compatible with interaction state.
    • State-level overpaint for selected regions plus a neutral base style for non-selected regions.

    When modifying highlight/colour behavior:

    • Prefer robust IDs and data-testid selectors for new controls.
    • Add both integration and E2E coverage, because highlight behavior can differ under mocked vs real browser rendering.
    • Commit authored documentation changes under documentation/; generated docs/ output is ignored by Git.

    Documentation

    This project uses TypeDoc to generate API documentation from TypeScript source code and comments. There is a User Guide to help users to use Ribocode.

    There is a CHANGELOG which summarises changes, particularly changes to the UI or key underlying functionality.

    How to Generate Documentation

    • Documentation is generated into the docs/ directory.
    • To generate or update the documentation, run:
      npm run docs
    • The documentation will be available as static HTML files in the docs/ folder.
    • npm run docs generates docs locally only; it does not deploy them.
    • Authored Markdown is maintained in documentation/; TypeDoc reads those files and README.md.
    • docs/ is generated output and is ignored by Git. Commit the authored files and configuration, not the generated output. Deployment publishes the generated files separately.

    Configuration

    • The TypeDoc configuration is in typedoc.json at the project root.
    • TypeDoc uses tsconfig.typedoc.json (via typedoc.json) so docs generation excludes test files and focuses on production API surface.
    • The entry point is the src/ directory.
    • You can customize the output and included files by editing typedoc.json.

    Deployment Recommendation

    • GitHub Pages deployment (npm run deploy) publishes docs together with the app because the build step copies docs/ into dist/docs (postbuild) before publishing dist.
    • For this repository, deployed docs are available at https://ribocode-slola.github.io/ribocode1/docs/index.html.
    • For forks, use https://<username>.github.io/ribocode1/docs/index.html.

    Docs-only Deployment

    • Use npm run docs:deploy to publish only API docs to the gh-pages branch under the docs/ folder.
    • Use npm run docs:deploy:dryrun to validate the same process without pushing.
    • These scripts run TypeDoc first (npm run docs) and then publish the generated docs/ output using gh-pages.
    • Use npm run docs:deploy:target to publish docs to an explicit repository URL from env config.
    • Use npm run docs:deploy:target:dryrun to validate targeted publishing without pushing.

    Targeted deployment configuration:

    • Set DOCS_GH_PAGES_REPO in .env or .env.production (production values override .env).
    • Example value: DOCS_GH_PAGES_REPO=https://github.com/<your-github-username>/ribocode1.git
    • This keeps shared scripts stable while allowing each developer to publish docs to their own fork.

    Destination URL rules:

    • The final URL is determined by the repository that receives the gh-pages push.
    • If push target is your fork (typical origin), docs will be at https://<your-github-username>.github.io/ribocode1/docs/index.html.
    • If push target is the upstream repository, docs will be at https://ribocode-slola.github.io/ribocode1/docs/index.html.

    How to confirm where deployment will go:

    • Run git remote -v and verify which repository URL is configured for origin.
    • npm run docs:deploy uses your configured git remote unless you override it with gh-pages options.

    Optional explicit target example:

    gh-pages -d docs -e docs -a -m "Docs: update API documentation" \
      --repo https://github.com/<your-github-username>/ribocode1.git

    Deployment

    The fork and shared repository have separate gh-pages branches. Choose the destination before deploying:

    • Testing on your fork (origin): Run git remote -v to confirm that origin points to your fork, then run npm run deploy. This publishes to the fork's gh-pages branch, not the official site. If GitHub Pages is enabled for that branch, the test PWA is available at https://<username>.github.io/ribocode1/. No release tag is needed.
    • Official deployment (upstream): An authorized maintainer deploys from the intended upstream source commit using npm run deploy -- --repo https://github.com/ribocode-slola/ribocode1.git. For a versioned release, follow the release checklist: run preflight before deploying, verify the live PWA, then tag the deployed source commit. A docs-only deployment does not require a new release tag; see Docs-only Deployment.

    Versioning

    Ribocode versioning is driven by package.json and package-lock.json.

    Source-file metadata

    The @version in a project-authored source file's header tracks that file, not the application release. New source files, including tests, start at 1.0.0. When modifying a file, update its @lastModified date to the date of the change in YYYY-MM-DD format and increment its version according to the scope:

    • Patch: a minor fix or small update, for example 1.0.0 to 1.0.1.
    • Minor: a more substantive change, for example 1.0.1 to 1.1.0.
    • Major: a complete rewrite, for example 1.1.0 to 2.0.0.

    Reset the patch number when incrementing the minor number, and reset both minor and patch numbers when incrementing the major number. If an existing project-authored source file lacks these fields, add them when modifying it. Do not treat file versions as application release versions or modify third-party or generated files solely to add metadata.

    Recommended bump commands

    From the project root, use one of the npm scripts:

    • npm run version:patch
    • npm run version:minor
    • npm run version:major

    These run npm version <level> --no-git-tag-version and update both package.json and package-lock.json.

    UI version display

    The app header version text is read directly from package.json in src/components/AppHeader.tsx, so no manual edit is required there when bumping versions.

    Release checklist

    The GitHub Pages PWA is where users run and install Ribocode. The upstream GitHub Releases page records versioned source snapshots and release notes; publishing a GitHub Release does not deploy the PWA.

    In the Ribocode root repository (not packages/molstar), keep origin pointed at your fork and use upstream for the shared repository. If upstream is not configured, add it and verify both remotes:

    git remote add upstream https://github.com/ribocode-slola/ribocode1.git
    git remote -v

    1. Bump the version using one of the commands above, update CHANGELOG.md, and run the relevant tests.

    2. Push the changes to your fork and open a pull request into upstream main.

    3. After merge, an authorized maintainer fetches upstream and checks out the exact merged commit in a clean working tree. Run npm run release:check before deploying. It checks that the checkout is clean and on upstream main history, that package.json has a matching CHANGELOG.md entry, and that the tag is available upstream. It prints the commit SHA, tag, and destination without creating a tag, deploying, or pushing.

      Copy the full SHA from the Commit: line. This identifies the source commit you are about to deploy, not the gh-pages commit generated by deployment. Use this SHA as <deployed-commit-sha> in step 5.

    4. Deploy from that checkout, explicitly targeting the shared repository so the build does not go to your fork:

      npm run deploy -- --repo https://github.com/ribocode-slola/ribocode1.git

    5. Wait for Pages to serve the new build and verify that the live PWA shows the expected version. From the same source checkout, run git rev-parse HEAD and confirm it matches the SHA you copied in step 3. If it does not match, stop and return to the deployed source commit before tagging. Then run the command below, using the copied SHA in place of <deployed-commit-sha> (omit the angle brackets):

      npm run release:tag -- <deployed-commit-sha>

      The command repeats the checks, verifies the supplied SHA matches the checkout, and creates and pushes only the matching annotated vX.Y.Z tag. It does not check the live PWA for you. If the push fails and the tag did not reach upstream, rerun the command after addressing the error; it can reuse an annotated local tag for the same commit.

    6. Confirm the release workflow succeeded and the new entry appears on the upstream Releases page. The workflow publishes notes from the matching changelog entry in the tagged commit. If publishing fails after the tag reaches upstream, inspect and rerun the workflow rather than pushing or moving the tag. If the workflow is not present on the tagged commit, publish manually using the existing upstream tag and changelog entry.

    The workflow matches tag pushes, validates the full vX.Y.Z format against package.json, and only publishes in ribocode-slola/ribocode1. Neither a branch beginning with v nor a tag pushed to a fork publishes an official release. A GitHub Release created manually on a fork stays there: a tag can be pushed elsewhere, but release notes and uploaded assets are not transferred.

    Session Fidelity Inventory (v0.17.x)

    This historical inventory records session save/load parity for the v0.17.x roadmap workstream. It is not a complete guarantee for later features; check the current session tests and implementation when changing session behavior.

    Parity Matrix

    Category Coverage
    Persisted + restored Dataset visibility per viewer/mode (AlignedTo/Aligned), representation list (type, colorTheme, visible), highlights (subunit/chain/residue), inspect toggles (subunit/chain/residue per viewer/mode), selected subunit/chain/residue(s), selection display mode + dim settings (per mode), zoom controls (global + per viewer), clipping controls (per viewer), fog settings (per viewer), camera snapshots (per viewer), sync enabled + active viewer, chain-finder queries, UniProt label toggle (legacy + per viewer), color-theme library + selected theme per mode, resolved UniProt gene-name cache.
    Persisted but restore has caveats Camera/clipping/fog only restore when corresponding dataset/plugin state is available. If required files are missing or loaded later, those values may restore partially. Legacy selectionDisplay payloads (single mode) are restored to both modes as a compatibility fallback. Inspect/highlight restoration depends on chain/residue IDs being present in the loaded structures.
    Not persisted (known gaps) Per-representation style parameters beyond type/colorTheme/visible (for example opacity sliders and other representation params), transient panel open/closed UI state, temporary diagnostics (realignment debug/status history), and ephemeral in-progress interaction state.

    Native Mol* residue highlights are saved separately from checked residues and the shared highlight toggle, with their dataset, source viewer, chain and residue IDs, and exact Mol* unit indices. On session load the structure hash, units and indices are checked before reconstructing the source selection and mirroring its markers. Sessions without this optional field do not infer native highlights from checked residues. If the structure is unavailable or incompatible, restoration logs a warning instead of broadening the selection. Residue selection IDs distinguish author numbers and insertion codes, including blank codes, so that mirroring and the residue controls do not conflate them. Additional chain slots retain residue selections by dataset and chain ID. Session exports associate each additional chain ID with its residue IDs, including empty selections; sessions without that optional data use the normal default selection. Changing or removing a slot cascades to later slots and clears their residue state and tracked native markers. All slots use ordered, per-dataset chain/residue selection state. An uninitialized residue selection is distinct from an explicitly empty one, so newly selected chains can default to all residues without changing an empty session selection. The session serialization format remains unchanged. Adjacent chain reordering swaps complete selection entries within one dataset; it does not use replacement handlers or cascade-clear subsequent slots. Native residue highlights and inspect targets follow their chain IDs, while alignment and shared-residue comparisons continue to use their existing slot positions.

    Round-Trip Guarantees

    • Save -> load restores practical analysis context for the common paired-viewer workflow:
      • what datasets are shown/hidden;
      • which representations are visible;
      • what selections/highlights/inspect toggles are active;
      • display mode and dim settings;
      • camera + clipping + fog controls.
    • Round-trip guarantees are validated by deterministic integration tests in src/App.integration.test.tsx, including a sync-on camera-restore regression check for preserving distinct viewer snapshots.
    • End-to-end parity coverage also includes e2e/session-load-sync-camera-order.e2e.spec.ts, which guards against Viewer B camera drift immediately after session load when sync is restored.

    Known Limitations and Fallbacks

    • Load requires external files and opens a required-file picker when session references cannot be resolved automatically.
    • Load All can restore from embedded files in the session payload (schemaVersion: 2) and is the preferred collaboration/share path.
    • When datasets cannot be reloaded, session UI state may still apply partially and the app surfaces a non-blocking alert.
    • Non-persisted state listed above is intentionally out-of-scope for current v0.17.x parity.

    Tests

    This project uses Vitest and @testing-library/react for unit and component testing. Vitest is a modern, fast test runner with native ESM support, ideal for Vite-based projects.

    Test File Structure

    • Unit/component tests: Use .test.ts or .test.tsx files placed alongside the code they test (e.g., App.test.tsx, components/ComponentName.test.tsx).
    • Integration tests: For flows involving multiple components or user workflows, use dedicated integration test files. For example:
      • App.integration.test.tsx: General integration tests for the main app UI and multi-component flows.
      • session.integration.test.tsx: Integration tests focused on session management (session save/load, file input, modal prompts, etc.).

    This separation keeps tests organized and maintainable as the codebase grows.

    Creating Tests

    • Test files should be placed alongside the code they test, using the .test.ts or .test.tsx extension.
    • Use descriptive test names and group related tests with describe blocks.
    • Example test file:
    import { render, screen } from '@testing-library/react';
    import MyComponent from './MyComponent';

    test('renders the component', () => {
    	render(<MyComponent />);
    	expect(screen.getByText('Hello')).toBeInTheDocument();
    });

    Running Tests

    Before requesting PR review, run npx tsc --noEmit --pretty false and npm run test:pr. The latter runs unit and integration tests once, then the standard browser E2E suite; it does not run the TypeScript check or force WebGL. Stop any dev server using port 5173 first so Playwright can start its own server. If the first suite fails, the E2E suite does not run. For alignment or viewer changes, also run the relevant forced-WebGL checks in the alignment testing reference.

    • To run the unit and integration suite once:
      npm run test -- --run
    • To run tests in watch mode:
      npm test -- --watch
    • To run the interactive UI test runner:
      npm run test:ui
    • To run a specific test file:
      npm test -- src/components/MyComponent.test.tsx

    End-to-End (E2E) Testing with Playwright

    This project uses Playwright for end-to-end (E2E) browser testing. Playwright enables automated UI testing in real browsers, ensuring that real-world user workflows (including session save/load and dataset handling) work as expected.

    E2E Test Structure

    • E2E tests are located in the e2e/ directory at the project root.
    • Real-world test datasets (e.g., 4UG0.cif, 6XU8.cif) are stored in data/input/.
    • Example E2E tests:
      • e2e/example-session.spec.ts: Demonstrates loading a dataset, interacting with the UI, and verifying session logic.
      • e2e/session-load.e2e.spec.ts: Covers the full session load workflow, including file selection modal and session restoration.

    System Dependencies for Playwright (Linux)

    Playwright's browsers (especially Chromium) require certain system libraries to be installed on Linux. If you see errors like:

    error while loading shared libraries: libnspr4.so: cannot open shared object file: No such file or directory

    You need to install the missing libraries. On Ubuntu/Debian, run:

    sudo apt-get update
    sudo apt-get install libnspr4 libnss3 libatk1.0-0 libatk-bridge2.0-0 libcups2 libdrm2 libxkbcommon0 libxcomposite1 libxdamage1 libxrandr2 libgbm1 libasound2 libpangocairo-1.0-0 libpango-1.0-0 libgtk-3-0 libxss1 libxshmfence1 libxfixes3 libxext6 libx11-xcb1

    Note: On some newer Ubuntu/Debian systems, libasound2 may be provided as libasound2t64. If you see a message like:

    Package libasound2 is a virtual package provided by: ... libasound2t64 ...

    then install it with:

    sudo apt-get install libasound2t64

    On Fedora/RHEL/CentOS, use:

    sudo dnf install nspr nss atk at-spi2-atk cups-libs libdrm libxkbcommon libXcomposite libXdamage libXrandr mesa-libgbm alsa-lib pango gtk3 libXScrnSaver libxshmfence libXfixes libXext libX11-xcb

    See the Playwright system requirements for more details.

    Installing Playwright

    Playwright and its test runner are project dependencies installed by npm install. Install the Chromium browser used by the configured E2E suite:

    npx playwright install chromium

    The package versions and lockfile determine the required browser revision. Check the installed package and the expected browser paths with:

    npx playwright --version
    npx playwright install chromium --dry-run

    The dry run does not verify that those browsers are installed or executable. The normal headless E2E suite uses the corresponding Chromium headless shell; an existing full Chrome binary alone may not be sufficient. Install with the project's own Playwright version after updating dependencies. If a download stalls or fails, capture the install output and check network, proxy and certificate settings; see the official browser download guidance. Updating Playwright changes the expected browser revision but does not itself fix a download or system-dependency problem. On WSL, a checkout in the Linux filesystem can avoid some issues associated with Windows-mounted filesystems.

    Running E2E Tests

    Note: Playwright E2E tests and unit/integration tests (run with Vitest) should be run separately. E2E tests require a real browser and dev server, are slower, and have different dependencies and environments than fast, isolated unit/integration tests. Keeping them separate ensures clarity, speed, and easier debugging.

    Summary:

    • Run unit/integration tests once with npm run test -- --run (npm test starts watch mode).
    • Run all E2E tests in strict mode with npm run test:e2e.
    • Run all E2E tests while reusing an already-running dev server with npm run test:e2e:reuse.
    • Run WebGL-focused E2E checks with npm run test:e2e:webgl (or npm run test:e2e:webgl:reuse).

    Playwright is configured with a webServer entry and starts npm run dev on port 5173. Tests navigate relative to Playwright's baseURL; if using an alternative configuration and port, update both baseURL and webServer together so tests run against the intended server.

    • npm run test:e2e uses strict mode (reuseExistingServer: false) and fails if 5173 is already in use.
    • npm run test:e2e:reuse sets PW_E2E_REUSE_SERVER=1 and reuses an existing dev server on 5173.
    • npm run test:e2e:webgl sets PW_E2E_FORCE_WEBGL=1 and runs WebGL-gated specs in single-worker mode with WebGL launch flags.
    • npm run test:e2e:webgl:reuse combines PW_E2E_FORCE_WEBGL=1 with PW_E2E_REUSE_SERVER=1.

    Troubleshooting Parallel E2E Failures

    Normal local runs can use multiple workers; CI and forced-WebGL runs default to one worker. If a normal parallel run fails or times out, stop other test runs and rerun with one worker:

    npm run test:e2e -- --workers=1

    This keeps the normal browser settings while changing the worker count. For forced-WebGL checks, use npm run test:e2e:webgl, which defaults to one worker and uses different browser launch flags. A serial pass can indicate concurrency or resource sensitivity, but does not prove the cause: investigate repeatable failures, including possible application or test races.

    Workers in one Playwright run share its dev server; they do not each start a server on port 5173. In strict mode, an occupied port prevents startup. To avoid conflicts, run independent suites one at a time, or give each its own server port and output directory. When changing ports, configure both baseURL and webServer together. Reuse mode can instead connect to an existing server.

    Expected skipped tests in normal (test:e2e) runs

    Seeing skipped tests can be expected and does not necessarily indicate failure:

    • Four visual-regression/manual-flow specs in e2e/representation-theme-switch-regression.e2e.spec.ts are skipped when WebGL is unavailable in the run environment.

    The native Reset Zoom test and Selection Mode + Reset Zoom test request software WebGL in standard E2E runs and compare the open clipping control with the effective camera radius. Their shared setup waits for Viewer B's Hide 6XU8 button before checking the camera fit. The visibility control can be present as a placeholder before the Aligned structure is ready.

    If you need those visual checks to run, use:

    npm run test:e2e:webgl
    # or with a pre-running dev server
    npm run test:e2e:webgl:reuse
    • To run all E2E tests:
      npm run test:e2e
      # reuse a running dev server (useful during local development)
      npm run test:e2e:reuse
      # or
      npx playwright test
    • To run a specific E2E test file:
      npm run test:e2e -- e2e/session-load.e2e.spec.ts
      # or (reuse mode)
      npm run test:e2e:reuse -- e2e/session-load.e2e.spec.ts
      # or
      npx playwright test e2e/session-load.e2e.spec.ts
    • To open the interactive Playwright Test UI:
      npm run test:e2e:ui
      # or
      npx playwright test --ui

    E2E Test Best Practices

    • Use data-testid or accessible selectors for robust element targeting.
    • Clean up test state between tests to avoid cross-test interference.
    • Document any new E2E tests and datasets added.
    • Prefer realistic user flows: test file selection dialogs, downloads, and UI prompts as a user would experience them.

    Session Round-Trip Regression Patterns

    • Keep Save and Save All selection payloads in parity for session fidelity. If selection schema is extended (for example chainId2, residueId2, residueIds2), update both save paths and both restore paths together.
    • Add integration coverage for session schema changes in src/App.integration.test.tsx before or alongside app changes. This catches regressions in serialized UI state quickly.
    • For Playwright session-load assertions, gate on readiness state before asserting UI labels. For sync-related flows, prefer polling the test API (window.__ribocodeTestApi.getSyncState()) and then asserting button enabled/text state.
    • Reuse shared session helpers in e2e/helpers/session-load.ts for loading fixture sessions and required files instead of re-implementing modal/file-input flows in each spec.
    • When a session E2E fails under a run that was manually interrupted (^C/SIGINT), re-run cleanly before triage; interrupted runs can report false failures across unrelated specs.

    Session and Selector Stability Notes

    • Prefer stable ID/testid selectors for repeated controls (Zoom, Highlight, Inspect) because label text is intentionally duplicated across Subunit, Chain, and Residue sections.
    • For session load/save/reload flows, wait for key controls (for example #session-menu-btn) before interacting after navigation or reload.
    • Long session workflows can exceed the default 30s test timeout under parallel workers; set a per-test timeout (for example test.setTimeout(60000)) for save/reload/load scenarios.
    • If Playwright times out before a test body runs (for example, while setting up context), set the timeout with test.describe.configure({ timeout: 120000 }) at spec or group scope. A test.setTimeout() call inside the test runs too late to cover fixture setup.
    • Wait for a readiness signal appropriate to the workflow, not just a filename label: filenames can appear before loading finishes. For the Aligned dataset, the enabled visibility control with an accessible label beginning Hide indicates that it is loaded.

    Retrospective: 0.16.2 Test Stabilization

    • Preserve product contracts before hardening tests. In particular, keep Load Aligned disabled until AlignedTo is loaded; changing this contract can make integration tests fail while masking the real regression.
    • Prefer structural selectors over label text for repeated controls. Column-scoped IDs and data-testid selectors are more reliable than role/name selectors when Show/Hide controls appear in both viewers.
    • Treat timeout increases as a last step, not the first step. Flaky tests were primarily caused by async UI transitions and selector ambiguity, not by timeout settings alone.

    Working from a fork

    Use origin for your fork and upstream for the shared Ribocode repository. If upstream is not configured in the Ribocode root, run git remote add upstream https://github.com/ribocode-slola/ribocode1.git once.

    Keep local main for syncing, and do your work on a separate branch. Update local main before starting a new branch. You can also sync it right after a pull request merges:

    git switch main
    git pull --ff-only upstream main

    --ff-only prevents an accidental merge commit. If local main has diverged, inspect the local commits before reconciling it; do not force-reset it as part of your routine. You do not need to update your fork's main to keep your local main current.

    Start each new change from the updated main with git switch -c my-change and commit on that branch.

    Before requesting review, run git fetch upstream from your feature branch. If upstream/main has moved in a way that could affect your work, or if the PR has conflicts, run git merge upstream/main and resolve any conflicts before testing. Merging is preferable on a shared branch because it does not rewrite history. If the merge changes the recorded Mol* commit, run git submodule update --init --recursive after making sure you have no uncommitted submodule work.

    Run the TypeScript, PR and relevant focused checks described in Running Tests on the resulting branch, push it with git push -u origin my-change, and open a pull request from your fork's branch into ribocode-slola/ribocode1:main. Record the test results in the PR and, when possible, have another contributor review before merging. There is no need to merge every unrelated upstream change.
